--------------------------------------------------------------------------------
1.2 — DATASET ACQUISITION
--------------------------------------------------------------------------------
  [ ] Register at UCI ML Repository, download WESAD dataset
      URL: https://archive.ics.uci.edu/dataset/465/wesad
  [ ] Extract all 15 subject folders (S2–S17) to /data/raw/WESAD/
  [ ] Verify each folder has .pkl file with signals + labels
      (BVP, EDA, ACC, label)
  [ ] Download DREAMER and DEAP from PhysioNet as supplementary [Secondary]
  [ ] Write loader script — load one subject, print signal shapes and label counts
  [ ] Plot sample HRV, EDA, and accelerometer traces for 3 subjects — visual sanity check

WHY THIS MATTERS:
  WESAD is the gold standard for wearable stress detection research — 15 real human
  subjects, real physiological stress, peer-reviewed, used in 200+ published papers.
  Using a credible dataset means your model's performance numbers are defensible to
  government reviewers. Without validated data, you are building on assumptions.

--------------------------------------------------------------------------------
1.3 — SIGNAL PREPROCESSING PIPELINE
--------------------------------------------------------------------------------
  [ ] BVP/PPG: band-pass filter 0.5–4 Hz to remove hand-motion artifacts
  [ ] Extract R-R intervals from PPG peaks (inter-beat intervals for HRV)
  [ ] Compute HRV features: RMSSD, SDNN, pNN50, LF/HF ratio, mean, std, range
  [ ] EDA: low-pass filter at 1 Hz, decompose into tonic + phasic components
  [ ] Compute GSR features: mean, std, peak count, peak amplitude, slope, rise time
  [ ] Accelerometer: magnitude = sqrt(x²+y²+z²), band-pass 0.1–0.5 Hz for breathing
  [ ] Compute motion features: mean magnitude, std, spectral entropy, breathing rate
  [ ] Apply 30-second sliding window with 5-second step across all signal streams
  [ ] Remove windows with >20% missing or flat signal (artifact rejection)
  [ ] Write unit tests for all preprocessing functions in /tests/test_preprocessing.py
  [ ] Run preprocessing pipeline on all 15 subjects — verify zero crashes

WHY THIS MATTERS:
  Raw watch signals contain motion artifacts, electrical noise, and gaps from
  sensor contact loss. Feeding dirty signals into a model means it learns noise
  patterns, not stress patterns. RMSSD is one of the most researched stress
  biomarkers in sports science and medicine — you need clean signals to compute it.

--------------------------------------------------------------------------------
1.4 — PERSONAL BASELINE CALIBRATION
--------------------------------------------------------------------------------
  [ ] Implement PersonalBaseline class with fit(), normalize(), save(), load() methods
  [ ] fit() computes per-user mean and std for each feature from 2 weeks of baseline windows
  [ ] normalize() converts features to z-scores relative to personal baseline
  [ ] Implement incremental update: EMA with alpha=0.05 so baseline evolves slowly
  [ ] Test: fit on S2 baseline windows, normalize S2 stress windows — verify z-scores > 2
  [ ] Store baseline on device only — raw biometrics never leave the watch

WHY THIS MATTERS:
  Two people can have identical HRV values — one is panicking, the other is calm
  because that is their normal. A population-average model cannot tell them apart.
  Personal baseline measures deviation from that person's own normal — far more
  sensitive and accurate. Primary reason this system will have lower false positive
  rates than any generic stress detector.

--------------------------------------------------------------------------------
1.5 — XGBOOST BASELINE CLASSIFIER
--------------------------------------------------------------------------------
  [ ] Create feature matrix: (N_windows, 16 features) from all preprocessed subjects
  [ ] Assign binary labels: WESAD label 2 (stress) → distress=1, all others → safe=0
  [ ] Train with scale_pos_weight=3 to compensate for class imbalance
  [ ] Leave-one-subject-out cross-validation (LOSO-CV) — train on 14, test on 1, repeat
  [ ] Compute SHAP values — plot top 10 most predictive features as bar chart
  [ ] Evaluate mean F1 > 0.78 on distress class across all LOSO folds
  [ ] Save model as baseline_xgb.pkl

WHY THIS MATTERS:
  Before spending days training an LSTM, verify that feature engineering is correct.
  XGBoost trains in minutes, and SHAP values tell you exactly which features predict
  distress. If XGBoost cannot reach 78% F1, something is wrong upstream — fix it
  here, not after 30 epochs of LSTM training.

--------------------------------------------------------------------------------
1.6 — LSTM DANGER CLASSIFIER
--------------------------------------------------------------------------------
  [ ] Implement WESADDataset PyTorch class: 30s windows, 5 signals, binary labels
  [ ] Implement DangerLSTM:
      2-layer LSTM, hidden=128, dropout=0.3, FC classification head
  [ ] Input shape: (batch, 300 timesteps, 5 signals) — BVP, EDA, ACC_x, ACC_y, ACC_z
  [ ] Output: softmax over [P(safe), P(distress)] — danger score = P(distress) × 100
  [ ] Training: AdamW lr=1e-3, ReduceLROnPlateau scheduler, 30 epochs
  [ ] CrossEntropyLoss with weights [1.0, 2.5] — penalize missed distress more
  [ ] Full LOSO-CV: train on 14 subjects, test on 1, repeat for all 15 subjects
  [ ] Target: mean F1 > 0.83 on distress class across all 15 LOSO folds
  [ ] Generate confusion matrix and ROC-AUC on held-out test set
  [ ] Save best checkpoint as best_danger_model.pt

WHY THIS MATTERS:
  The LSTM is your production model — runs on the watch companion every 5 seconds
  for the entire life of the product. Unlike XGBoost which sees statistics, LSTM
  processes the raw sequence and learns temporal patterns: 'GSR spiked while HRV
  dropped sharply in last 8 seconds'. This time signature is what makes LSTM
  consistently outperform feature-based models on physiological stress detection.

--------------------------------------------------------------------------------
1.7 — CONTEXTUAL GATING LAYER
--------------------------------------------------------------------------------
  [ ] Implement ContextualGate class with:
      process(raw_score, lat, lon, multi_signal_agree, sustained_secs)
  [ ] Multi-signal agreement: require 2 of 3 signals (HRV, GSR, breathing)
      in distress range simultaneously
  [ ] Duration gate: sustained score >= 70 for minimum 15 seconds before SOS fires
  [ ] GPS safe zone: Haversine distance check against saved safe zones
      — raises threshold to 85 inside safe zones
  [ ] Rolling smoother: rolling average of last 10 readings (50-second window)
  [ ] Dismiss window: 10-second cancel window after first trigger
      — user double-taps to dismiss
  [ ] Test exercise scenario: elevated HRV + breathing, low GSR sustained 20s
      → must NOT trigger
  [ ] Test genuine distress: all 3 signals elevated 20s, unknown location
      → MUST trigger

WHY THIS MATTERS:
  A model with 83% accuracy produces false alarms roughly 1 in 6 predictions.
  In a safety system, every false alarm dispatches a police drone unnecessarily —
  wasting resources and eroding trust. The gating layer adds context the ML model
  cannot know. This is the difference between 83% model accuracy and 95%+ real-world
  precision.

--------------------------------------------------------------------------------
1.8 — MODEL EXPORT AND OPTIMIZATION
--------------------------------------------------------------------------------
  [ ] Export LSTM to ONNX format using torch.onnx.export()
  [ ] Validate: ONNX outputs must match PyTorch outputs within 0.001 tolerance
      on 100 test samples
  [ ] Apply PyTorch INT8 dynamic quantization — target 4x model size reduction
  [ ] Benchmark: 1000 forward passes, measure mean + std inference time
      Target: mean < 50ms
  [ ] Write model card:
      training dataset, LOSO-CV performance, known failure modes
      (exercise, panic attacks, medical conditions), data requirements
  [ ] Commit all models, scripts, and model card to GitHub

WHY THIS MATTERS:
  A model that only runs on your laptop is not deployable. ONNX export makes it
  runnable on any device — companion phone, Jetson Orin Nano, future smartwatch chip.
  INT8 quantization shrinks model 4x — faster inference and less battery drain.
  Model card is what government technical reviewers read first to assess whether
  you understand your system's limitations — honesty here builds credibility.

================================================================================

--------------------------------------------------------------------------------
2.1 — PROJECT INFRASTRUCTURE SETUP
--------------------------------------------------------------------------------
  [ ] Install dependencies:
      langchain, langgraph, langchain-openai, fastapi, uvicorn, sqlalchemy,
      psycopg2, pydantic
  [ ] Set up PostgreSQL with PostGIS via Docker:
      docker run -p 5432:5432 -e POSTGRES_PASSWORD=pass postgres
  [ ] Enable PostGIS: CREATE EXTENSION postgis; in psql
  [ ] Create drone station registry schema:
      station_id, name, lat, lon, drone_count, available_drones,
      battery_levels, last_maintenance
  [ ] Seed with 10 mock police station records at realistic GPS coordinates
  [ ] Implement and test geospatial query:
      find nearest N stations from lat/lon, filtered by drone_available=true

WHY THIS MATTERS:
  PostgreSQL with PostGIS handles geospatial queries in milliseconds. When SOS
  fires, the system has under 2 seconds to find the nearest available drone station.
  A Python loop over a list of stations would never meet that requirement.

--------------------------------------------------------------------------------
2.2 — LANGGRAPH AGENT GRAPH DESIGN
--------------------------------------------------------------------------------
  [ ] Define SharedState TypedDict:
      victim_location, danger_score, drone_status, nearest_station,
      flight_path, mission_status, malfunction_flag, handoff_complete
  [ ] Create LangGraph StateGraph with all 10 agent nodes wired together
  [ ] Define conditional edges:
      danger threshold check, malfunction check, mission close check
  [ ] All agent input/output types defined as Pydantic models — never raw strings
  [ ] Draw complete agent graph diagram — save to docs/agent_graph.png

WHY THIS MATTERS:
  Drawing the full agent graph before writing code forces you to confront every
  edge case. The StateGraph and Pydantic typed outputs mean every agent
  communicates in structured data — not fragile strings that break when an LLM
  rephrases its response.

--------------------------------------------------------------------------------
2.3 — ALL 10 AGENT IMPLEMENTATIONS
--------------------------------------------------------------------------------
  [ ] Agent 1  — Danger Score:
      receives biometric score, decides go/no-go, updates state
  [ ] Agent 2  — SOS Broadcast:
      sends structured alert payload to police API and emergency contacts
  [ ] Agent 3  — Station Finder:
      queries PostGIS registry, returns ranked stations by distance + battery
  [ ] Agent 4  — Path Planning:
      A* routing with battery-aware cost, no-fly zone avoidance
  [ ] Agent 5  — Dispatch:
      sends MAVLink-formatted launch command to drone API
  [ ] Agent 6  — Tracking:
      polls victim GPS every 5s, updates drone waypoint if drift > 100m
  [ ] Agent 7  — Malfunction Monitor:
      polls telemetry every 500ms, sets malfunction_flag on fault
  [ ] Agent 8  — Handoff:
      finds ahead-station, dispatches Drone 2, transfers context packet
  [ ] Agent 9  — Scene Intelligence:
      receives vision feed, returns scene classification to pipeline
  [ ] Agent 10 — Management Notification:
      sends all state changes to dashboard WebSocket

WHY THIS MATTERS:
  Each agent has exactly one job. Single-responsibility design means when something
  breaks in production, you know immediately which agent failed and why. Each agent
  is independently testable — unit-test path planning without running the whole
  pipeline. This is production engineering, not a hackathon project.

--------------------------------------------------------------------------------
2.4 — OPENROUTER LLM CONFIGURATION
--------------------------------------------------------------------------------
  [ ] All LLM calls:
      base_url='https://openrouter.ai/api/v1', api_key from OPENROUTER_API_KEY env var
  [ ] All agent outputs typed as Pydantic models — zero raw text parsing anywhere
  [ ] Implement tenacity retry:
      3 retries, exponential backoff, rule-based fallback if all retries fail
  [ ] Test end-to-end: run one full agent LLM call, verify Pydantic output,
      verify retry on simulated timeout

WHY THIS MATTERS:
  Using OpenRouter instead of direct OpenAI keys means you can switch LLM providers
  in one line of code — if OpenAI has downtime during a real emergency response,
  you fall back to Claude or Mistral without any code changes. Pydantic-typed outputs
  guarantee downstream agents receive machine-parseable decisions.

--------------------------------------------------------------------------------

--------------------------------------------------------------------------------
4.1 — SCENE CLASSIFICATION MODEL
--------------------------------------------------------------------------------
  [ ] Download Google Open Images V7: 5000 outdoor + 5000 building/indoor images
  [ ] Train MobileNetV3-Small:
      80/20 split, 20 epochs, Adam lr=1e-4, augmentation (flip, brightness, rotation)
  [ ] Evaluate: accuracy > 92% on validation set, inference < 15ms per frame
  [ ] Save model as scene_classifier.pt
  [ ] Test on 20 photos taken yourself: 10 outdoor, 10 buildings — verify correct

WHY THIS MATTERS:
  Scene classifier makes the first decision on arrival: open ground or building?
  Open → hover and track. Building → orbit and map. Get this wrong — drone uses
  wrong strategy. 92% accurate means only 1 in 12 arrivals uses wrong mode.

--------------------------------------------------------------------------------
4.2 — BUILDING ENTRY/EXIT DETECTION
--------------------------------------------------------------------------------
  [ ] Collect and annotate training images: doors, gates, windows, stairwells, corridors
  [ ] Annotate in Roboflow (free tier) — export YOLOv8 format bounding boxes
  [ ] Train YOLOv8-nano: 50 epochs, img size 640. Target: mAP@0.5 > 0.72
  [ ] Implement orbital scan:
      drone rises to 15m, performs 360-degree orbit, detects entries
  [ ] Compute GPS coordinate of each detected entry from drone GPS + depth sensor
  [ ] Transmit GPS-tagged entry/exit map to dashboard WebSocket in real time
  [ ] Test on real building photos: at least 3 doors detected in each test image

WHY THIS MATTERS:
  This module directly saves police officers' lives. An officer who enters without
  knowing all exits is at risk of ambush. Your drone maps every visible door, gate,
  and window and transmits GPS coordinates before police arrive. Most visually
  impressive feature for government demonstration.

--------------------------------------------------------------------------------
4.3 — PERSON DETECTION AND TRACKING
--------------------------------------------------------------------------------
  [ ] Deploy YOLOv8-medium for person detection (pretrained COCO weights — no retraining)
  [ ] Install ByteTrack multi-object tracker — maintains persistent person IDs through occlusions
  [ ] Configure ByteTracker: max_age=30, min_hits=3, iou_threshold=0.3
  [ ] Victim identification: person whose GPS best matches watch GPS at arrival time
  [ ] Behavior analysis: flag rapid approach to victim, restraining motion as suspect
  [ ] Test tracking across 5 video clips: IDs maintained through 30-second clips with occlusions
  [ ] Stream all bounding boxes, IDs, and role labels to dashboard WebSocket in real time

WHY THIS MATTERS:
  When drone arrives, multiple people may be in scene. System must identify victim
  and track all persistently. ByteTrack maintains IDs even through occlusions —
  if threat actor ducks behind a car and reappears, same tracking ID is maintained.
  This makes video feed actionable intelligence, not just confusing footage.

--------------------------------------------------------------------------------
4.4 — NIGHT VISION MODE
--------------------------------------------------------------------------------
  [ ] Compute ambient brightness from RealSense color stream mean pixel value
  [ ] Automatic switch: if mean brightness < 40 lux → activate IR depth mode
  [ ] Apply CLAHE enhancement to low-light RGB frames before running YOLO detection
  [ ] Test in simulated dark room: person detection accuracy must remain > 80% in IR mode

WHY THIS MATTERS:
  Most assaults happen at night. A drone that cannot see in dark is not a safety
  system — it is a daylight demonstration. The RealSense D435i has active IR sensing
  that works in complete darkness. Without this module: 12-hour gap in coverage daily.

--------------------------------------------------------------------------------

  [ ] Implement GPU temperature monitor: throttle to 20 FPS if GPU temp > 80°C
  [ ] Commit all TensorRT engine files to /vision/engines/ in repository

WHY THIS MATTERS:

  The Pixhawk is the drone's nervous system. An uncalibrated flight controller cannot
  distinguish true horizontal from tilted surface, cannot read GPS accurately, cannot
  synchronize all four motors — leading to unstable hover, drift, and crash.
  Calibration sequence must be followed IN ORDER — each step depends on the previous.
